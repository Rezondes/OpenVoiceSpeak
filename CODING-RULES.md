# Coding and layout rules

General rules for C# projects with an Avalonia UI: how the source is laid out and named, and which design rules every change follows. They hold for any such project. Each project keeps its own additions in a file `CODING-RULES-<Project>.md` next to this one: which folders the rules cover, its folder layout, its shared helpers, its kept nested types, its exceptions to these rules and the decisions behind them. Where the project file is stricter than this file or names an exception, the project file wins. This file is meant to be read on its own; the project file is read together with it.

## Purpose and scope

- Every type is found by its name: the file is named after the type, the folder after the namespace.
- The rules apply to every `.cs` and `.axaml` file of the folders the project file lists. Files with an `<auto-generated>` header and anything under `bin/` and `obj/` are exempt, and so are the resource and asset folders whose paths the project file names as fixed; partials that source generators add need no file of their own (rule 4).
- Every commit builds with zero warnings, passes the full test suite and passes the rule checker (§Rule checker).
- Every commit stays reviewable in 15 to 25 minutes: at most about 400 non-mechanical changed lines.
- Moves and renames are behaviour-neutral and never share a commit with a logic change. A behaviour change is listed in the commit that makes it.
- Persisted files and the wire carry no CLR type names, so moves and renames do not change them: wire discriminators, error codes and JSON property names stay, and persisted files stay loadable with equal stored values. Full CLR type names in diagnostic texts (exception messages, crash logs) may change with a namespace or a name.
- A public getter of a persisted record is written to its file, so new checks on persisted records are methods, never getters, and a commit that adds or removes such a getter lists it.

## Files, types and folders

1. **One top-level type per file, file name = type name**, without exceptions: also exceptions, coupled pairs (a reader and its writer, an encoder and its decoder) and internal helpers.
2. **Generics:** a generic type's file has the bare name, without arity or parameters (`Choice.cs` for `Choice<T>`).
3. **Interfaces** keep the `I` prefix in type and file name. An interface exists only when the tests use a real fake of it or when it has several production implementations; an interface with one implementation that nothing fakes is replaced by the concrete class or a delegate.
4. **Partial types:** a type may span several files only as `Type.Part.cs` in one folder, and only when it is large for a reason that cannot be removed; a part never hides a second responsibility, which gets a class of its own. The project file lists the types allowed to be partial. Partials that source generators add need no file.
5. **Nested types:** only `private` nested types used by their container alone stay nested. Every other nested type is a top-level type of its own, `internal` when it was private and must be reachable from outside. Nested types stand at the end of their container, and the project file lists the ones kept. A public event uses `EventHandler<T>` or a top-level delegate, never a nested public delegate.
6. **Namespace = folder** in every project, file-scoped (`namespace A.B;`), with explicit `using` lines and no new `global using`.
7. **No git-ignored folder names.** No folder is named like a pattern the `.gitignore` ignores at any depth (with the default .NET `.gitignore`: `Backup*`, `Log`, `Logs`, `Debug`, `Release`, `bin`, `obj`, `x64`, `artifacts`, `publish`, `Generated_Code`), so the `.gitignore` needs no exception for a source folder.
8. **No namespace segment named like a type** of the same project, or like a type the code in that namespace uses. Every new folder name is checked before it is used. The rule works both ways: no folder is named like a type, and no type is named like its folder. Avalonia example: a namespace ending in `.Animation` hides Avalonia's class `Avalonia.Animation.Animation` from every file below the enclosing namespace (C# finds a namespace there before the file's `using Avalonia.Animation;`), so such a folder is named `Animations/`.
9. **Exceptions:** each project has an `Exceptions/` folder; a base exception and its subclass get one file each.

## Avalonia UI

10. **Views end in `View`** and live in `Views/`, except `App` and the main window. Reusable controls live in `Controls/` and keep their names (no suffix).
11. **Every type in `ViewModels/` is a view model and ends in `ViewModel`**, also an item view model that is only read. Bound records and enums go to `Models/`, dialog contracts to `Dialogs/`, non-UI helpers to `Services/` and `Collections/`.
12. **User-facing text comes from the localization resources** (`.resx`), never from a literal in a view, a view model or a server answer.
13. **XAML prefixes:** each namespace has one fixed XAML prefix, used in every file that names one of its types, also in type selectors (`ctl|Spinner`); the project file lists them. XAML has no compiler `using`: a type in a new namespace needs its prefix in every file that names it.
14. **Composition roots:** `Program.Main` and `App.OnFrameworkInitializationCompleted` build the services (the clock, the logs, the settings, the hardware) and hand them to the view models through their constructors; a view model builds none of them. Only the two roots read the statics they hand over. Dialogs and other window-bound parts are set on the view model once the window exists, as delegates, so the view model knows no view type.

## Names

15. **Names say exactly what a thing is.** A type contains only what its name says; a type that does more is split. No project type name is the plural of another project type name (`X`+`s`, `X`+`es`, `Xy`/`Xies`; framework types do not count). No bag names: no type name ends in `Helper`, `Helpers`, `Util`, `Utils`, `Utility`, `Utilities`, `Manager`, `Common` or `Misc`, and `Service`, `Info` and `Data` appear only with a subject. Methods are verbs and do not repeat the name of their type. Methods that return a `Task` end in `Async`. One concept may have a code name that differs from its wire name.
16. **English in code.** Identifiers, log lines and exception messages are English. The wire carries codes, and the texts the client shows for them are localized in the client (rule 12).
17. **The compiler enforces naming where it can:** an `.editorconfig` with naming rules (the `I` prefix of interfaces, the `Async` suffix, PascalCase types and members) and `EnforceCodeStyleInBuild` (the built-in analyzers, no package).
18. **No em dash** (U+2014) anywhere: code, comments, XML docs, resources, docs and commit messages. Use a colon, a comma, parentheses or a new sentence.
19. **Rule classes** are static, pure classes that decide one domain question. They are named after the concept they decide plus `Rule` or `Access` (`DiscountRule`, `DocumentAccess`), or `Rules` when a class holds several rules of one subject; their methods are verbs or predicates (`Evaluate`, `IsEditable`). **One concept, one word:** the domain's word is used in code, resources, docs and tests alike; a wire or persisted name differs from the code name only where the project file allows it and a test pins it.
20. **Every local, parameter, field and lambda parameter name is a readable word that says exactly what it holds.** Banned: one-letter names (`s`, `r`, `a`, `b`, `c`, and `e` of an event handler, which is `args`) and abbreviations such as `vm`, `ct`, `cts`, `ms`, `ex`, `ctx`, `cfg`, `msg`, `btn` (`channel => channel.Name`, not `c => c.Name`; `cancellationToken`, not `ct`). Accepted acronyms, as words alone or in compounds: Id, Ui, Ip, Tcp, Udp, Json, Http, Utc, Url (`userId`, `ip`). A discarded parameter is `_`; a loop counter names what it counts (`index`, `row`, `column`). Generic type parameters (`T`) and type names follow rule 15.
21. **No tuple return types** (also not `Task<(...)>` or `IEnumerable<(...)>`), and no `out` parameters as a substitute; the `bool TryX(..., out T)` pattern stays allowed. A method with several results returns a named record; a record used inside one class may be a private nested record (rule 5); hot paths (per packet, per audio frame) use a `readonly record struct`. Private one-line helpers count too. Reason: a named record keeps a later change small, because a field can be added without touching every caller.
22. **No primary constructor with guard clauses in new classes:** a class whose constructor validates its arguments uses the classic constructor form. Records and classes without guard clauses may use primary constructors.
23. **XML docs are required** on every type and every non-private member: `GenerateDocumentationFile` is on, and CS1591 is a warning under the zero-warnings rule.
24. **Renames are allowed** when a rule needs them; test methods may be renamed and split. **Comments name types, not paths;** a document that names a source path (README, notices, website comments) changes in the same commit as the move.

## Async and concurrency

1. Async all the way: no `.Result`, `.Wait()` or `GetAwaiter().GetResult()` outside `Main` and the synchronous adapters of tests.
2. Every async method that does IO takes a `CancellationToken` as its last parameter and passes it on.
3. No `async void` except event handlers.
4. A lock is held as briefly as possible and never across an `await`. A new synchronisation scheme needs a comment that explains it and a test that proves it.
5. **No `Thread.Sleep` with a non-zero argument** in production code. The only exceptions: (a) a deliberate block in a test or a throwaway script and (b) `Thread.Sleep(0)` to yield the CPU. A dedicated thread (audio, input, a log writer's retry) that must pause waits on a wait handle that stop and wake can end (`WaitHandle.WaitOne(timeout)` or `ManualResetEventSlim.Wait(timeout)`), so stopping never waits for a sleep to run out and its `Join` needs no timeout that exists only because a sleep cannot be woken; such a blocking wait is marked `// clock: real time`.
6. **One injected clock:** every decision that depends on time reads the `TimeProvider` built in the composition roots (`Task.Delay(delay, timeProvider, token)`, `new PeriodicTimer(period, timeProvider)`, `timeProvider.CreateTimer(...)`). Any other use of a clock, timer or timed wait is marked at the end of its line with `// clock: <kind>`; the project file lists the kinds.

| Need | Use |
|---|---|
| waiting, also a cancellable wait | `await Task.Delay(...)` with a `CancellationToken` |
| periodic work | `PeriodicTimer` (no drift) |
| waiting for a condition or event | `SemaphoreSlim`, `AutoResetEvent` / `ManualResetEventSlim` or `TaskCompletionSource` (no polling with sleep) |
| scheduled background work | `System.Threading.Timer` |

## Tests

- The test folders mirror the source folders, each with the folders of its project; namespaces follow the folders.
- A test file named after a type is named `<Type>Tests.cs` and sits in that type's folder; it follows renames. A test file named after a feature keeps its name and sits in the folder of the type it mostly drives.
- Helpers used by several test files go to `TestSupport/`. Single-use helpers get their own file next to their test. A test of a test helper sits next to it. Temporary folders are created per test and deleted in `Dispose`; no static state is shared between test classes.
- Every test name has three parts, `Subject_Condition_Outcome`; without a condition the middle part names the state. Each test checks one behaviour. A test is split only when its name names two outcomes and its setup is cheap (no network server, under 100 ms).
- Tests are deterministic: a manual `TimeProvider` or frame counts instead of `Task.Delay`, `Thread.Sleep`, `DateTime.Now` or wall-clock bounds. A fixed wait becomes a clock advance plus a drain; a check that something does not happen waits a bounded time on the manual clock; poll loops use one shared wait helper; an awaited task that a broken build would leave pending is bounded by a test-side hang guard; windows opened by a headless Avalonia test are closed in `finally`. The `Thread.Sleep(1)` yields in UI poll loops of tests may stay.
- No source seam exists only for waiting.

## Rule checker

The project's rule checker guards these rules with one command, which the project file names. It checks every rule it can check statically: what the compiler checks (rule 17, rule 23, the zero warnings) is left to the build, and what neither can check is a point of §Review checklist. A new rule names its check in the same commit; a rule without a check is a wish.

## Review checklist: design principles

Every review of new or changed code answers each point below for that change, names the file and line for every "no", and either fixes it or records why not.

**Naming (rules 15, 16, 18 to 22)**
- Does every new or renamed type contain only what its name says?
- Red flag: a type name that is the plural of another project type name, e.g. `Customers` next to `Customer`.
- Red flag: a bag name, e.g. an `OrderHelper` or a `UserService`; name what the type holds or decides (`OrderPricing`).
- Red flag: a method that is no verb or repeats its type's name, e.g. `Subscription.IsSubscriptionActive` (`IsActive`).
- Red flag: a `Task`-returning method without `Async`.
- Red flag: a non-English log line or exception message in new or moved code.
- Red flag: a one-letter or abbreviated name, also a lambda parameter or the `e` of an event handler, e.g. `c => c.Name` or `ct`.
- Red flag: a tuple return type or an `out` parameter used instead of a record, e.g. `(Export? Export, string Code)`.
- Red flag: a rule class not named `...Rule`, `...Access` or `...Rules`, or one concept with two words.
- Red flag: a primary constructor with guard clauses in a new class.
- Red flag: an em dash anywhere.
- Red flag: user-facing text as a literal in a view model.

**Errors**
- Is every input validated where it enters (a frame, a file, a setting, an import)?
- Is no exception caught that the code cannot handle? Is every swallowed exception logged or commented with its reason?

**Async (§Async and concurrency)**
- Async all the way, a `CancellationToken` as the last parameter of every async method that does IO, no `async void` except event handlers?
- No lock held across an `await`? A new synchronisation scheme is the KISS red flag.
- No `Thread.Sleep` with a non-zero argument in production code; a dedicated thread waits on a wait handle marked `// clock: real time`?

**DRY (don't repeat yourself)**
- Does the change copy logic that exists elsewhere (a shared helper or rule class the project file lists)? Use or extend the one place.
- Does a new setting, sound, key action or request need edits in several lists that must agree? Prefer one table or one mapping method over parallel switches.
- Red flag: the same predicate in client and server (e.g. "is this subscription active"); put it in the shared project.

**DDD (domain-driven design)**
- Is a domain rule (who may do what, when something is full or locked, a retry policy) placed in a pure rule class next to its siblings, not inside a view model, a view or a request handler?
- Does the code use the domain words of the protocol and the specification?
- Are invariants of persisted records kept by one method on the record or a rule class, not only by a handler?

**TDD (test-driven development)**
- Were the tests written first and seen red (state it in the review notes)?
- Is every new rule tested where it lives, as a fast unit test, with end-to-end tests (network, headless UI) only for the acceptance path?
- Is every test deterministic (§Tests)? Is no new static state shared between test classes?

**BDD (behaviour-driven development)**
- Does each acceptance criterion of the change have a test whose three-part name states the behaviour?
- Does each test check one behaviour, so its name says what broke when it fails?
- Is each manual check listed as manual?

**KISS (keep it simple)**
- Is this the simplest code that meets the criteria (no framework or generic layer with one user; no interface unless the tests use a real fake of it or it has several production implementations)?
- Are deliberate shortcuts marked with a `ponytail:` comment naming the limit and the upgrade path?
- Red flags: closure state machines with several captured mutable variables, a new synchronisation scheme, mixed clock sources in one class.

**SOLID**
- **Single responsibility:** does a class gain a responsibility it did not have? Red flags: a class over about 400 lines or a method over about 40 lines; state or a pure rule added to a class that already handles requests (it gets a class of its own). Extract a collaborator or a child view model instead.
- **Open/closed:** how many places change to add one more request, dialog, sound, setting or key action? A new `case` in a central switch needs a test that every member is handled.
- **Liskov substitution:** does a subtype keep every promise of its base (no `NotSupportedException` overrides, no stricter preconditions)?
- **Interface segregation:** does a consumer receive more than it uses (a whole state object, session, dialog set or engine)? Pass the narrow piece (a delegate, a record, or an interface that rule 3 allows).
- **Dependency inversion:** are time (`TimeProvider`), the UI thread (`post`), the network (`send` or a connection factory), files and devices passed in rather than created inside the class or read from statics (`DateTime.Now`, `Environment.TickCount64`, singletons, static mutable state)? Is there one injected `TimeProvider`, created in the composition roots, for every decision clock, with every other use of a clock marked (§Async and concurrency, rule 6)?

**Security** (for code that handles requests, files or secrets)
- Is every size and count bounded?
- Does the server decide every right, and does nothing a caller may not see reach the answer (counts, error texts and lookup values included)?
- Are secrets (passwords, tokens, keys) never written to logs or answers?
