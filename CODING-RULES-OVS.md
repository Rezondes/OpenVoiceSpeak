# Coding and layout rules: OpenVoiceSpeak

The OpenVoiceSpeak part of the coding rules. The general rules for C# projects with an Avalonia UI are in `CODING-RULES.md` next to this file; this file holds what is specific to OpenVoiceSpeak: where the general rules apply, the project's additions and exceptions to them (numbered by the general rule they belong to), the target layout, the kept nested types, the shared helpers, the rule checker, the project's review red flags and the decisions behind all of it. Read it together with `CODING-RULES.md`; where the two differ, this file wins.

The rules and the decisions behind them were made on 5 October 2026 (§Decisions (5 October 2026), IDs A1 to M9), on 6 October 2026 (§Decisions (6 October 2026), IDs N1 to N30) and on 8 October 2026 (§Decisions (8 October 2026), IDs W1 to W7, the general rules taken over from the WiDaO project); where they differ, the decisions of 8 October 2026 (as amended on 9 October) win over those of 6 October, which win over those of 5 October (N1). On 12 October 2026 the general rules were moved into `CODING-RULES.md` and renumbered there; §History maps the old rule numbers that the decisions below still use.

**Status.** The first, structural refactoring (5 October 2026) is finished; items marked "introduced by the refactoring" are the ones it added. A second refactoring (6 October 2026) applies the design principles and the naming rule to the existing code (N1, N2). Until it is finished, parts of the code and some type names in the tables below still show the state before it; the tables name the types as they are and follow each rename and move in the commit that makes it. Items marked "not yet introduced" do not exist before that refactoring adds them. New and changed code follows these rules.

## Scope

- The rules apply to every `.cs` and `.axaml` file in `src/`, `tests/`, `tools/render-icon` (A1 c) and the rule checker's `tools/rule-lint` and `tools/rule-lint-tests` (12 October 2026). They do not apply to `website/`, `Assets/`, `Localization/*.resx`, `Styles/` as resources, or `runtimes/` (their paths are fixed in the csproj, XAML, tools and tests, F6).
- Every commit builds with zero warnings and passes the full suite, `SourceLayoutTests` included (a known flaky test, listed in the refactoring plan, may fail once if it passes alone).
- Moves and renames are behaviour-neutral and never share a commit with a logic change (N4). Behaviour changes where the design principles need it, listed in the commit that makes it (N1). Wire discriminators, `ReasonCodes` values and JSON property names stay (N9), and persisted files stay loadable with equal stored values (N11). Full CLR type names in diagnostic texts may change with a namespace or a name (accepted under A4).
- A commit that adds or removes a public getter of a persisted record lists it (N11).

## Target layout

### OVS.Shared

- `Protocol/` keeps `WireProtocol` (what client and server must agree on: the version and the log page size), `ProtocolLimits` (the bounds both keep: lengths, ranges, transfer sizes) and `ProtocolDefaults` (the start values); together they were `ProtocolInfo` (N18), whose server-only values went to `ServerTuning`. It also keeps `ReasonCodes` (was `Codes`), `TextRules`, `ServerIconFormat`, and later `Base64Text` (§Shared helpers).
- `Protocol/Framing/`: `ProtocolJson`, `FrameReader`, `FrameWriter` (D7).
- `Protocol/Messages/`: see §Protocol messages.
- `Voice/` stays flat, one type per file (D8): `PacketType`, `PacketDirection` (was `Direction`), `VoiceHeader`, `VoiceCrypto`, `SeqCounter`, `ReplayWindow`, `LossReport`, `PingPayload`, `LossWindow`, `RelayPayload`.
- `Permissions/`: `Permission`, `WellKnownGroups`, `PermissionExtensions`, and the rules server and client share, `GroupRules`, `ChannelAccess` and `ChannelCapacity` (N1; `ChannelCapacity` moved from the server's `Rules/` in Step 22). `Identity/`: `ClientIdentity`, `CertFingerprint` (D9).
- `Moderation/`: `BanStatus` (moved from the client, N18) and its rule `BanStatusRule`.
- `Logging/`, `Exceptions/`, and later `IO/` and `Net/` (§Shared helpers). `Net/` also holds `ControlConnection` with its `MessageReceivedEventArgs` and `DisconnectedEventArgs` (Package 194): public events of a shared type use `EventHandler<T>` (CA1003), the client's own types keep `Action`. Since Package M11 it also holds `StateMirror` and `ChannelPair`, which the client and the web manager share.

The others are in `Messages/<Area>/` with namespace `OVS.Shared.Protocol.Messages.<Area>` (D2, D3, D4):

That is 2 + 90 = 92 types. Data records and enums go to the area they belong to (`LinkInfo` to `Links`, `UserInfo` to `Users`, `ServerSnapshot` to `Connection`). A comment that describes a group of records goes into the summary of each record it describes (D6), since one type per file leaves no shared place for it. The area names avoid every clash (C2, C3): `ServerBackups` instead of `Backups` or `BackupFiles` (both ignored by `Backup*/`), `LogAccess` instead of `LogFiles` (the class `OVS.Shared.Logging.LogFiles`, now `LogFileWriter`), `ServerInfo` instead of `ServerSettings` (the server class `ServerSettings`), `VoiceRelay` instead of `Voice` (the namespace `OVS.Shared.Voice`). New messages go into the area they belong to and get their `[JsonDerivedType]` line on `Message`. Renaming a record never changes its discriminator, the `ReasonCodes` values or the JSON property names, and needs no protocol version bump (N9); `WireFreezeTests` pins them with literal lists.

### OVS.Server

- The root keeps `Program`, `ServerConfig` (E4), `ControlServer`, `Session` and its `SessionOutbox` (the frames for the write loop; no folder named `Session/`), `ServerHost`, `ServerStores` (the file stores of one run: `Open` makes them and runs the crash cleanups of uploads, half written backups and log exports, in that order; `ServerState` receives them and creates none), `AdminToken`, `ServerTuning` (it holds all limits, not only throttling, E5, and the server-only values that were in `ProtocolInfo`: the chat burst and window, the log line cut, the search timeout and the log download cap), `RestartSchedule` (when the daily automatic restart is due and the wait for it, N8) and `RequestShape`. A frame that is a JSON object but no valid request gets no stand-in type: `ControlServer` passes its request id and problem to `ServerState.HandleMalformed` (overrides E6).
- `Data/`: `DataStore` and the backup types `BackupStore` (create, list, find, delete, the quota, adopting a finished upload, removing its own half written archives at start), `BackupArchive` (one archive: write, read and check, manifest, entries), `BackupManifest`, `BackupContent` (the checked contents; applies itself to the data folder), `ServerIconStore` (E2), `UploadFolder` (upload ids, their hidden files, removing unfinished uploads at start), `BackupUpload` (one session's upload in progress, N8) and `SaveScheduler` (when the data file is written: at once, debounced, retried, at most once a minute per key, and on close; N8). `Data/Records/`: the persisted types `ServerSettings`, `ChannelRecord`, `ChannelLinkRecord`, `UserRecord`, `BanRecord`, `ServerData` (E1).
- `State/`: `ServerState` and its parts (§ServerState).
- `Permissions/`: `PermissionRules`, `GroupRecord` (E3). `Rules/`: the pure request rules of the server, one class per concept (`ChannelSettingsRule`, `ChannelLinkRule`, `ModerationRule`, `ServerLimitsRule`) and the `Refusal` they return (N7). `Throttling/`: `RateLimiter` (it limits requests too, so it is not in `Voice/`, E5), `SessionThrottle` (one session's request, list, costly and chat budgets and the flood rule, N8), the guessing limits `PasswordGuessLimit` (wrong server passwords per address group), `AdminTokenGuessLimit` (wrong admin tokens per address group) and `ChannelPasswordGuessLimit` (wrong channel passwords per session and channel), and `NewIdentityLimit` (new identities per address group), N8. `Logging/`: `LogReader` (lists, pages and searches the log files), `LogExporter` (writes a download snapshot from the reader's listing and removes what a crash left behind, N8) with its result record `LogExport`, `ServerLogWriter` (`WriteServerLine`, `WriteChannelLine`, through the shared `LogFileWriter`), and one session's `LogJobQueue` and `LogDownload` (N8). `Security/`: `StoredPassword` (E7, introduced by the refactoring as `PasswordHash`; a value object since N10). `Tls/`, `Voice/` (`UdpVoiceServer`, `VoiceRouting` and one session's `SessionVoice`, N8), `Exceptions/`.

### ServerState

All parts of `ServerState` live in `src/OVS.Server/State/` with namespace `OVS.Server.State` (B2 a, B3, B4 a). A folder named `ServerState` would clash with the class (C3), and the parts must share one namespace.

What `ServerState` holds (N7): the request handlers of every area, also of backups and logs, because they need the sessions, persistence, the one lock and the shared `Require`, `Fail`, `Throttle*` and `Page`. What has its own state or is pure leaves `ServerState`: a pure rule goes into a rule class in `Rules/` (or `PermissionRules` for rights), which the handler calls before it changes anything; the invariants of the persisted data are methods of `ServerData` (`FindProblem`), a piece with its own state (saving, guessing limits, upload folders, log export) becomes a class of its own that `ServerState` holds. There are no `*Service` classes and no role interfaces for `ServerState` (nothing fakes them, N3). The global lock stays one lock.

| File | Holds |
|---|---|
| `ServerState.cs` | fields, constructor, settings, `Handle` with the table `Routes` (one line per request type: its handler and whether it is a transfer, which the request budget exempts; `DispatchTests` fails for a request type without a line or without a test factory), `HandleMalformed`, the helpers without broadcast and persistence; `BroadcastUser`, `BroadcastSettings` and `BroadcastGroups` stay here next to the per-recipient helpers they use (`Info`, `Moderates`, `SettingsInfo`, `GroupInfos`) |
| `ServerState.Connections.cs` | connections: `Admit`, `Remove`, `CloseAll`, `LogRejected`, `RemoveLocked`, the statistics, `ChannelLog`, `ChannelName` |
| `ServerState.Throttling.cs` | the request limits: `Admissible`, `Throttle`, `ThrottleList`, `ThrottleHeavy`, `OnGetServerIcon` |
| `ServerState.Persistence.cs` | `WriteData` (the save action of `SaveScheduler`: the pruning, `BeforeSave`, the write), `FlushPendingSave`, `BeforeSave`, `PruneGuests` (the daily gate `nextPrune` and its log line) |
| `ServerState.Broadcast.cs` | `Broadcast`, `BroadcastExcept` |
| `ServerState.Voice.cs` | voice |
| `ServerState.Admin.cs`, `.Backup.cs`, `.Channel.cs`, `.Chat.cs`, `.Link.cs`, `.Log.cs`, `.Moderation.cs` | the command handlers of each area (formerly `Commands/*Commands.cs`) |

The saving (`Persist`, `PersistSoon` with the save timer and retry, close) is such a piece and is `SaveScheduler` (N8): `ServerState` holds it as `saves`, gives it the one lock and `WriteData`, and its timer takes the same lock; the pruning before a save is `ServerData.PruneEndedBans` and `ServerData.PruneGuests`, the count of a blocked join `BanRecord.CountBlockedAttempt`. The guessing limits are such pieces too, one class per limit: `PasswordGuessLimit` (held as `passwordGuesses`), `AdminTokenGuessLimit` (`adminTokenGuesses`), `ChannelPasswordGuessLimit` (`channelPasswordGuesses`, `internal` so a test sees that `RemoveLocked` and `CloseAll` forget a session's counts) and `NewIdentityLimit` (`newIdentities`), all under the one lock (N8); their numbers are in `ServerTuning`, their log lines stay in the handlers. A new request area gets a part `ServerState.<Area>.cs` in `State/` for its handlers only; its state and its pure rules go into classes of their own (N7).

### Client

- **Root:** `Program`, `ClientOptions`, `App`, `Splash` (F5). `Program.Main` and `App.OnFrameworkInitializationCompleted` are the composition roots (N14): `Program` holds the one clock (`Program.Time`), makes the client log and reads the settings once (`Program.Settings` with `Program.SettingsWarning`; the UI language comes from them); `App` builds the system's audio hardware (`WasapiHardware`; the view model gets none with `--no-audio`, the debug API lists its devices anyway) and hands it with them and the keyboard's key state (`KeyPoller.IsKeyDown`) to `ClientServices.CreateMainViewModel`, whose container makes the key poller, the own tones (`SoundLibrary`, whose samples it hands to the engine), the capture filters on the client log (`NativeCaptureFilters`), the audio engine on that hardware, the trusted server fingerprints (`TrustedServerFingerprints`), the logo cache, the leave timer on that clock and the real connect (`ServerConnector`, which asks the view model's `ConfirmTofu` and logs the answer, Step 30d5), then the view model, which lists the hardware's devices on the settings page. The view model builds none of them, reads the clock as `Time` and disposes the key poller and the engine with itself. The dialogs (`Dialogs`, `ConfirmTofu`) and the updater are set on it once the window exists, since every dialog lives in the window's overlay. Outside the two roots the client reads time only through that clock, except on a line marked with one of the kinds of N14; `OneClockTests` enforces it, and that only the roots read their hand-over statics (`Program.Log`, `Options`, `Settings`).
- **`Audio/`** keeps `AudioEngine` and `SpeakerReportThrottle` and has subfolders (F2):
  - `Capture/`: CapturePipeline, StereoInput, FrameChunker, SincResampler, SampleConversion (static: the microphone's interleaved float samples read as mono (`ReadMono`, with the one-sided rule) or stereo (`ReadStereo`), and the stereo `Downmix` that the capture and the echo canceller's far end in `PlaybackLoop` share)
  - `Processing/`: AutoGain, NoiseSuppressor and EchoCanceller (Package 178: both load their filter from `ovs_audio`: RNNoise through nnnoiseless, AEC3 linked statically), VolumeCurve, NativeCaptureFilters (the noise suppressor and echo canceller each new capture gets, a missing library logged once and not tried again; `MainViewModel.Create` builds it on the client log and hands it to the engine, which attaches it in `ConfigureCapture` with its `AudioEngine.EchoDelayMs`, the playback target `PlaybackLoop.TargetBufferMs` plus `WasapiHardware.SpeakerBufferMs` and `CapturePipeline.MicBufferMs`)
  - `Transmit/`: TransmitRule, TransmitMode, AudioContent, VoiceActivityDetector, LossAdapter
  - `Codec/`: AudioFormat, VoiceEncoder and VoiceDecoder (Packages 175, 179: the faces of libopus in `ovs_audio`)
  - `Playback/`: VoiceMixer, SoftLimiter, JitterBuffer, ActiveSpeaker, ReceiveStats, PlaybackLoop (the playback thread: started on demand, it mixes the voices and the tones for the speaker up to its `TargetBufferMs` or on its own 20 ms clock, feeds the echo canceller's far end and ends when nothing is needed; the speaker is the `DeviceLifecycle`'s, closed under the engine's lock; the engine holds it in its private field `playbackLoop` and keeps the speakers event, the output level and the tests' hooks as one-line accessors)
  - `Devices/`: AudioDevice, AudioDirection, IAudioHardware, WasapiHardware, IPlaybackBuffer (Package 173: the open speaker the playback loop fills and asks for a failure; the real one is `Rust/NativeSpeaker`, the tests' `FakeSpeaker`), DeviceWatcher, DeviceLifecycle (opens a configured capture and the speaker, closes them and reopens them after device changes, under the engine's lock, which its "under gate" members assert; the engine holds it as `AudioEngine.DeviceLifecycle`, chooses the devices and restarts them through it, configures each new capture (its filters, the send path, the settings) through a callback and joins its warnings into one notice in `AudioEngine.Report`), CaptureSource (where the capture comes from, the microphone or the test tone in its place (`ToneHz`), and the capture opened from there (`Capture`): opened, set up through the engine's callback and started, and closed, under the same lock; when it opens and when the tone changes (`DeviceLifecycle.SetTone`) stay the lifecycle's, which builds it and holds it as `DeviceLifecycle.CaptureSource`)
  - `Sounds/`: SoundEvent, SoundSynth, SoundQueue (Package 174: hands each tone once to a speaker that plays the sounds itself and still mixes it for the far end), SoundPlayer (which notification sound plays, how loud, from which samples, and the preview of one sound's setting; the engine holds it as `AudioEngine.Sounds`), SoundImport, SoundLibrary
  - `Rust/` (Package 172): NativeAudio (the native audio library `ovs_audio`, loaded by hand once per name with its ABI version checked; a missing or foreign library is an `Error`, never an exception; it holds the exports as function pointers) and the types over its exports: NativeSpeaker (Package 173: the speaker on a native render thread; a close from another thread waits without a lock until a write has left the native code), NativeObjectHandle (Package 175: a native object freed through its own free export, also by the finalizer), NativeJitterStats (the jitter buffer's counts as laid out natively); `Playback/JitterBuffer` and `Codec/VoiceDecoder` are the managed faces of the native jitter buffer and libopus decoder; NativeMixerSnapshot (Package 176: what the client reads of the native mixer); `Playback/VoiceMixer` and `Playback/SoftLimiter` are the faces of the native mixer and limiter, and a native speaker renders the mixer itself (`IPlaybackBuffer.AttachMixer`) while the playback loop only follows it; NativeMicrophone (Package 177: the microphone on a native capture thread with a ring of one second; `CapturePipeline.FromMicrophone` waits on its event and feeds the managed chain)
- **Native audio library** (`native/ovs_audio`, Rust, Packages 172 to 180, A177 to A182): the exports are a C ABI, each named `ovs_audio_…` and run through `guard`, so no panic crosses into C#; `src/core/` makes no OS call (a cargo test checks it), the device layers sit behind traits; a native audio thread never calls into .NET (C# waits on an event or polls); the audio threads allocate nothing in steady state. It is the client's only native library (Package 180: no Concentus, `rnnoise.dll` or `ovs_aec.dll`; NAudio stays for the device listing and watcher (`CoreAudioApi`) and the WAV and MP3 readers of `Sounds/SoundImport` and `SoundLibrary`; `ArchitectureTests` checks it); when it cannot load, the engine runs without devices as with `--no-audio` and names the reason once (`AudioEngine.Unavailable`, one notice, one log line). Every component linked into it is in `THIRD-PARTY-NOTICES.md` (`NoticesTests`). Before a commit that touches it: `cargo test` and `cargo clippy --all-targets -- -D warnings` in that folder, and `build.ps1` with the new `$Expected` (the checked-in DLL is the build of the committed sources).

### Tests

- The test folders mirror src (J2): `Shared/...`, `Server/...`, `Client/...`, each with the folders of its project; namespaces follow the folders. `Website/` and `TestSupport/` stay; `SmokeTests.cs`, `SourceLayoutTests.cs` and `PlanReferenceTests.cs` are at the root, the last two with their scanners `SourceLayout.cs` and `PlanReference.cs`.
- A test file named after a type is named `<Type>Tests.cs` and sits in that type's folder; it follows renames (J3: `ConnectionStatsViewModelTests`, `PendingActionViewModelTests`). A test file named after a feature keeps its name (J4) and sits in the folder of the type it mostly drives.
- Helpers used by several test files go to `TestSupport/` (`MotionWait`, `FakeHttp`, `DeviceRig`, `SentRequests.LastRequestId<T>`, `UiTestApp` with the `[assembly: AvaloniaTestApplication]` attribute, and the helpers of §Shared helpers). Single-use helpers get their own file next to their test (`CollectingSink`, `Unseekable`, `ShotVariantsAttribute`, `WebsiteScene`) (J1). A test of a test helper sits next to it (`TestSupport/LayoutAssertTests.cs`). Temporary folders are created per test and deleted in `Dispose` (`TempDirectoryTest`); no static state is shared between test classes.
- Test methods may be renamed and split (N21); a test is split only when its name names two outcomes and its setup is cheap (no TLS server, under 100 ms, N24). Every test name has three parts, `Subject_Condition_Outcome`; without a condition the middle part names the state (N22). The test class `WebsiteShots` keeps its name for the README filter (L4).
- Links from acceptance criteria to tests live only in PLAN.md and docs/archive/PLAN-ARCHIVE.md, in the Tests section of each package, in these forms: `Class > "Method"`, `File.cs > "Method"`, a header line with the methods as bullets below it, `[Theory] "Name"`, a class alone (it covers the criterion), and `file > "text"` for the website (the file exists and contains the text). `PlanReferenceTests` resolves every reference by reflection (N19); it also reads `Class.Method`, takes a method without a class from the class named before it on its line or on the last header or numbered item, skips note lines starting with "(" (such as "(as built: ...)", also indented) and a test named after "ersetzt" or "replaces", lists a reference that no test covers any more, with its reason, in `Uncovered`, and a span that looks like a test but is none, with its reason, in `NoTest`. Every checked criterion has a `(manuell|manual|spike ...)` marker right after its ID, a resolving reference of its package that names it, or an entry in `NoTestPossible` with a one-line reason (N20, Step 35); a stale entry fails too.
- PLAN.md and docs/archive/PLAN-ARCHIVE.md change only in the test name and path references of their Tests sections, never in the text of an acceptance criterion (N21, L1); a package moves from PLAN.md into the archive only at the user's word.
- Waiting (N23): no src seam exists only for waiting. A fixed wait becomes a clock advance plus a drain; a check that something does not happen uses `AsyncWait.AssertStaysFalseAsync(condition, duration, reason)`; poll loops use `AsyncWait`; an awaited task that a broken build would leave pending (a test on a manual clock) is bounded with `HangGuard.Bound`; the `Thread.Sleep(1)` yields in UI poll loops stay.

## Review checklist: project red flags

The review answers every point of `CODING-RULES.md` §Review checklist. This section adds the OpenVoiceSpeak specifics. The red flags come from the audits of 5 and 6 October 2026 (weakest points: single responsibility, domain rules inside view models and `ServerState`, behaviour specs not linked to tests, names that say less or more than the type holds).

**Naming (N2, N5; general rules 15, 16, 18 to 22)**
- Red flag: `Limits` also held the server's tuning values (hence `ServerTuning`, N8).
- Red flag: `AudioDevices` next to `AudioDevice` (dissolved since, N12), or `KeyActions` next to `KeyAction` (split since into `KeyActionTraits`, `KeyActionLabels` and `KeyBindingMatcher`).
- Red flag: a method that is no verb, e.g. `ServerState.ChannelLog(...)`, which writes a line (`WriteChannelLog`); a `Task`-returning method without `Async`, e.g. `ServerViewModel.DropUser` (`DropUserAsync`).
- Red flag: a German log line or exception message in new or moved code, e.g. `"Channel angelegt von ..."` in a moved handler.
- Red flag: a tuple return such as `(LogExport? Export, string Code)`.

**Errors**
- `SafeFile.DeleteQuietly` is the documented exception to "every swallowed exception is logged or commented".

**DRY**
- The one places to use or extend: a helper in §Shared helpers, a rule in `PermissionRules`, the server's `Rules/` or the shared `GroupRules`, `ChannelAccess`, `BanStatusRule`, the settings mapping `AudioEngine.Apply` with `ApplyCaptureSettings(CapturePipeline, ClientSettings)` and `SoundPlayer.GainFor` for the sound settings (guarded by `AudioEngineSettingsTests`).

**DDD**
- A domain rule (who may do what, when a channel is full or locked, which sound fits which event, reconnect policy) is not placed inside a view model, a view, `ServerState` or `Session`.
- The domain words are those of the protocol and PLAN.md (Channel, Link, Group, Lock, Separator, Ban, ServerMute, Deafen).

**TDD (N23)**
- Waiting: clock advance plus drain, `AsyncWait.AssertStaysFalseAsync`, `AsyncWait`, `HangGuard.Bound`; UI poll loops yield with `MotionWait.Pause()`, never a sleep.

**BDD (N19, N22)**
- Each acceptance criterion of the package has a test that the package's Tests section in PLAN.md references (N19); the test code carries no criterion comments or traits. Each manual check is listed as manual in PLAN.md.

**SOLID**
- **Single responsibility:** red flags are `ServerState`, `Session`, `MainViewModel`, `AdminViewModel`, `ServerViewModel`, `AudioEngine` growing further, and state or a pure rule added to a `ServerState` part (it gets a class of its own, N7). The admin page already composes `LogsViewModel`, `LinkMatrixViewModel`, `UsersAndBansViewModel`, `BackupCardViewModel`, `ServerSettingsViewModel`, `ServerIconViewModel` and `GroupListViewModel`.
- **Open/closed:** e.g. every `Request` subtype is dispatched (`DispatchTests`).
- **Interface segregation:** red flag: a consumer receives the whole `ServerState`, `Session`, `DialogCallbacks` or `AudioEngine`.
- **Dependency inversion:** the display switch, once the static `Motion.IsAnimated`, is the window's attached `Motion.DisplayProperty`; the composition roots are `Program.Main` and `App.OnFrameworkInitializationCompleted`, with every other use of a clock marked per line with one of the kinds of N14 (`OneClockTests` checks the client).

**Security**
- Sizes and counts are bounded by `ProtocolLimits` and `ServerTuning`.
